# 队友出图流程：当前接入与源码交接

这次收到的 `drawing-pipeline.zip` 是重庆案例的**结果包**，不含说明文档列出的 `pipeline.py`、`native_export.py`、`geometry.py`、`sheet.py`、`selection_round1.py`，也不含原始 `.max`、依赖锁定或源码许可文件。因此 KANPACE 当前接入的是可追溯的第一轮**选柜与外形核对结果**，不是 3ds Max 自动提取和出图算法。Web 不能凭这个 ZIP 对新项目重新出图。

## 现有操作

技术员打开工厂端某个项目的「图纸与构件」，在「队友出图包核对」导入 ZIP。页面显示候选柜体、已选对象范围及已有的 PNG 草稿；SVG/DXF 作为文件下载。若项目没有上传内容 SHA-256 完全一致的原始 `.max`，页面标记「未与本项目源模型核对，仅供参考」。这个核对包不会改写项目构件、BOM、成本、排程或生产任务。项目完成发货后不能再导入，但已有核对资料仍可查看。

服务端接口如下，项目编号必须与页面当前项目一致：

| 接口 | 用途 |
| --- | --- |
| `POST /api/projects/{id}/drawing-pipeline/import` | 提交 `filename`、`content_base64`、`expected_revision`；仅接受 ZIP 结果包 |
| `GET /api/projects/{id}/drawing-pipeline` | 查看候选、核对草稿、来源关联状态和限制 |
| `GET /api/projects/{id}/drawing-pipeline/assets/{packageId}/{preview\|svg\|dxf}` | 查看 PNG 或下载 SVG/DXF |

导入时检查归档路径、展开大小、格式版本、来源与几何/清单/选择记录的 SHA-256 关系，并只保存核对所需的 JSON 与图纸。原归档的 HTML、日志、模型网格与可执行内容不会部署到网页或执行。文件按工厂数据目录和项目分开存储，资产读取再次核验项目编号。无论源文件是否匹配，响应都保持 `review_only=true`、`manufacturing_release=false`、`can_dispatch=false`。

## 拿到源码后的真实算法接入

队友需提供完整的 `tools/drawing_pipeline/` 源码、测试、依赖版本/锁定文件、第三方许可清单，以及重庆回归用原始 `.max` 的受控访问方式。请同时说明这些代码与产物的商用权属。以上文件应从队友工作树导出，不应从当前 ZIP 的 HTML 或 JSON 反推实现。

接入顺序：

1. 在授权的 Windows 3ds Max 工作机运行 `pymxs` 原生索引和几何提取；Web 只提交项目、源文件指纹和任务状态，不能在普通 Python/浏览器假装读取 `.max`。
2. 用项目隔离的任务目录保存场景索引和几何包，校验原始模型、索引、候选目录、选择记录之间的指纹；不要沿用重庆固定路径或节点编号。
3. 由技术员在 Web 核对柜体范围、正面、数量与实际订单/现场尺寸；只选中模型范围并不等于确认生产数量。重新出图后仍先进入工程核对。
4. 把第一轮外形核对图与后续制造图分开。要转成可生产构件，仍须核对材料、板厚、孔槽、五金、装配节点、施工依据并由工程师签审。不得把“出图成功”映射成“可下料/可派工”。

当前结果包仅有 CQ-01 的早期草稿 PNG/SVG/DXF，15 组候选也只覆盖原模型的局部展示布置；这既不是完整订单拆单，也不是制造级图纸。技术事实以现有包内的 `review_manifest.json`、`verification.json` 和代码迁移说明为准。接入源码时保留上述项目隔离、来源核验和人工工程审核边界。
