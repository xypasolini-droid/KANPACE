# KANPACE 工厂配置中台审计

审计日期：2026-09-07。依据当前源码只读审计；未修改生产代码、未启动/重启实例、未读写客户业务数据。文件位置以源码根目录为基准，行号为审计时位置。

**结论：已有可复用的工厂协同执行底座，缺的是把这些能力组合成“工厂配置方案”，并经过预览、审核后安装到指定工厂。** 不需要为展柜、机械、工程现场各造一套 ERP，也不能把现有左上角类型切换当作已经完成工厂适配。

## 应复用的对象模型

现有主链已经明确：

```text
独立实例 → 工厂 → 班组/人员/工作中心
                     ↓
企业模板版本 → 项目工作包 → 工作对象 → 工序任务
                                      ↓
                         物料/开工条件/实绩/异常/验收/交付
```

继续使用 `factories`、`teams`、`people`、`workcenters`、`workflow_templates`、`project_workflows`、`tasks` 及 production 记录，不新造另一套订单和工单数据库。

建议只增加两类控制对象：

1. **工厂配置方案版本**：方案编号、schema/version/hash、行业基础包、企业对象叫法与类型、工序模板、资源别名、必要资料/检查字段、功能入口、原表列映射、审核记录。方案草稿可来自复制行业包、Excel 辅助提取或助手建议；来源与未决项保留。
2. **实例配置安装回执**：目标 instance/factory、方案版本与 hash、导入后的模板/资源 ID 映射、安装请求号、配置变更清单、启用时间和状态。控制端只管理方案及开通记录，默认不复制各厂订单、图纸、账号口令与实绩。

通用方案中使用 `wood_team`、`assembly_station` 等资源别名；安装时绑定目标厂真实 ID。不能把 A 厂 person_id/workcenter_id 直接复制到 B 厂。技能先做“企业叫法→模板规范工种字符串”的显式映射；后续若改为稳定技能 ID，应单独迁移，避免仅改显示名就让既有派工失配。

## 最小闭环配置字段

| 配置层 | 第一轮必需字段 | 留给订单运行时填写 |
|---|---|---|
| 实例/身份 | 工厂名、场景、独立实例标识、管理员、方案版本 | 日常新增账号和人员变动 |
| 工作对象 | 对象叫法、对象编号规则、首批可用对象类型、数量口径、交付批次叫法 | 实际柜号/设备号/区域、数量、位置、图纸 |
| 工艺路线 | 稳定 node_id、名称、规范工种、前序、开工检查、验收要求、是否质量放行、可选工作中心别名 | 该订单的技术要求、工程版本和审核记录 |
| 资源 | 本厂技能别名映射、人员/班组/工位映射、已确认每日容量；未知明确留空 | 当天缺勤、临时借调、现场阻断 |
| 时间 | 企业工作日历、估时单位与依据、未知项清单 | 实际时长、预计到料、临时优先级 |
| 资料与交接 | 必需文件用途、对象与图纸关联规则、交接/验收的必填项 | 施工图、效果图、局部页、实物进度和异常说明 |
| 原有表格 | 表名/来源系统标识、稳定外部编号列、订单/人员/物料/报工列映射与单位 | 每次上传原表及差异确认 |
| 页面/终端 | 本厂默认入口、启用模块、对象标签、工牌首页必要字段/允许动作 | 当前任务、实际图片、负责人和剩余数量 |

已有 `planning.py:54` 日历是**每实例一套工作日 weekdays**，不是每班组独立轮班日历；`planning.py:74`、`scheduling.py:167` 已核对人员/工作中心日容量。第一批直接复用实例日历即可，不要把待实现的夜班/节假日复杂班表放进必需配置。

工程现场若按 12.5 平方米计量，不能把现有工作对象整数数量直接改成小数而影响整件报工。首轮以“一个明确区域工作包”为整数执行对象，把面积/长度作为技术计量字段；要支持按工程量计酬/进度时再独立增加计量口径与校验。

## 从“开通空空间”到“生成可用现场平台”的最短路径

**第一步：选择/复制配置方案。** 控制端选择展柜、机械或工程现场的行业参考，再填本厂对象、实际工种、典型节点和原表列映射。只保存方案草稿，不创建生产任务。已有三套 DAG 直接作为基础素材。

**第二步：用一张典型订单预览。** 复用 `validate_nodes`、`validate_objects` 和纯计算的 `compile_tasks`，在内存或隔离临时 Store 中生成图形流程、任务卡/工牌卡、资料缺项、人员匹配和估时依据。结果明确显示节点串并行、哪些对象适用哪些路线以及待核对项；不能为了让预览变绿而填演示人员、默认工时或推测材料。

**第三步：主管核对并安装配置。** 确认的应是“将增加/映射哪些工种和工作中心、采用哪版路线、显示哪些页面、哪些信息仍缺”，而不只是工厂名称确认。安装接口验证方案 hash、目标实例和资源版本；同 request_id 重试返回同一安装回执。控制端注册记录在子实例完成事务和认证检查之后标为 ready；失败留可重试状态，不产生半套已启用配置。

**第四步：在本厂运行第一单。** 子实例首次打开就显示本厂名称、对象叫法、已装企业模板、资料缺项和下一步。真实订单工作包仍走人工技术复核→发布→分派→开工检查→执行→验收；“配置安装完成”不等于“生产任务已发布”。

中台的快速生成目标应以“该厂第一次拿到可核对的工种任务和图册用了多久、需要多少次手工映射”衡量，而不是生成了多少菜单。

## 应优先修正的五处

1. **实例场景成为服务端事实。** 独立实例返回固定 factory_id/type/profile_version，`workspace.js` 在子实例锁定本厂场景或改为明确的厂内业务视图，避免 localStorage 还保留另一种工厂类型。控制端的行业预览与子实例的生产空间应是不同入口。
2. **把资料完整性计算下沉为只读 API。** 目前 readiness 主要在 `static/factory-setup/app.js:10`。新增服务端配置预检结果供向导、助手和老板入口共用；返回字段缺失、来源、阻断原因及操作入口，不能把“资料齐全”与真正 start/release 门禁混为一谈。
3. **增加配置预览与安装状态，不改变工单引擎。** 可新增配置模块封装 `operations` 的现有校验/编译/保存，在预览时不调用会写任务的 `save_workflow`。preview_token 应覆盖方案 hash、对象输入、目标实例、资源版本；确认前状态变化则要求重新预览，复用迁移 impact_token 的思路。
4. **明确同一工作包目前只能一条完整对象路线。** `compile_tasks` 对每个对象复制所有节点且依赖仅在对象内部。不能把“机械子装配→整机汇合”或“区域隐蔽验收→另一组区域安装”误报为已支持。最小扩展先支持对象选择已发布路线和显式工作对象间依赖引用，经全图无环/来源校验后编译；没有规则的对象必须停留待配置，禁止按名称猜路线。
5. **菜单按配置收敛、权限仍在服务器。** 工厂 profile 决定默认入口和可用模块，账号权限决定允许操作；可见项取两者交集。工牌继续使用“项目/对象/当前动作/剩余数量/图册”通用卡，不为三行业复制三套固件页面。配置选项不能解除质量 Web 验收、版本或关闭项目等既有约束。

## 审核、版本与隔离必须保留的边界

- 行业参考、企业方案草稿、已审核方案版本、实例安装版本、项目工程/流程版本分别记录；不能用一个“模板版本”字段代替全部状态。
- 首轮复制配置仅把定义和资源映射交付目标实例；不跨客户搬运真实图纸、人员账号、报价或生产记录。共享同库的多个 `factory_id` 仍是组织归属，不能作为租户隔离承诺；隔离客户使用 `factory_instances` 的独立实例。
- 已启用配置版本不可原地修改。新增版本先预览受影响对象/节点/在制任务；在途项目沿用旧版，用户选中的项目才走现有 `migration_preview/migrate_workflow`。受影响实绩或未闭环返工继续阻断自动迁移。
- 尚未产生生产记录的配置安装失败可以重试/弃用；已经产生实绩的版本变更须向前修订，不通过删除记录“回滚”。
- 助手可以整理企业术语、列映射和候选工序，输出同一预览结构；确认动作仍调用有权限、版本与幂等校验的业务接口。配置 Agent 不直接编辑 SQLite、执行任意脚本或替技术员放行工程。

## 最小验收样例

用三个合成空实例各跑一张最小工作包即可验证配置能力，无需导入客户全量资料：展柜验证木作/五金/玻璃并行后总装；机械验证两类子装配显式汇合（未做跨对象扩展前应提示不支持）；现场验证作业面交接和隐蔽验收阻断。每例验证方案草稿不写任务、预览过期拒绝、安装重试不重复、不会出现他厂资源、只有审核后发布任务、新版不改变旧在制任务、工牌能显示对应任务资料。

本次未运行这些新配置验收；它们是下一轮实现的完成标准。现有相关测试文件 `tests/test_factory_instances.py`、`tests/test_factory_setup_frontend.cjs`、`tests/test_operations.py` 可继续作为回归基础。
