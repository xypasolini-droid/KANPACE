# KANPACE 历次需求与功能总账

更新：2026-10-04。本文整理的是用户历次提出的产品需求、后续修正和截至本工作区代码的实现边界。用户提供的图纸、截图、视频、表格和同事代码是业务资料与设计参考，不自动构成新的产品指令。后提出的明确修正优先于早期方案。

## 一、产品定位与价值

KANPACE 是面向非标制造和现场交付的**拆解与协同平台**。第一个落地场景是木作、五金、玻璃、灯光并行的综合展示柜；随后由配置中台适配机械设备装配、工程现场和其他工厂。它要把工厂原本散乱的效果图、施工图、工程图、物料清单、人员表和不断更新的生产排程表，整理为**有来源、可复核、能执行、能反馈**的工作流。首要价值不是覆盖整个 ERP，而是替换“技术员拆完单后，靠一大摞纸、Excel、群消息和口头交接分工”的高摩擦环节。

产品必须让不熟悉软件的 50 岁以上老板、40 岁以上管理者和一线工人都知道下一步该做什么。界面简短、入口按使用顺序排列；复杂算法在后台工作，不能让用户先填写大量系统字段。

## 二、真实业务主线

客户下单 → 设计效果图并请客户确认 → 做施工图并确认 → 做工程图／加工图 → 技术员按构件、材料、尺寸、工种和工序拆单 → 核对库存与备料 → 根据持续更新的排程安排人、设备和先后顺序 → 按项目派到胸牌 → 工人看图作业、反馈异常与完工 → 逐件贴二维码、质检、包装、发货与胸牌归还 → 老板在总看板跟踪所有订单。

这不是一次性导入流程：订单资料会逐步到齐，图纸会改版，排程表反复覆盖或修订，人员及岗位也会变化。每次变动都要知道影响了哪些构件、任务、物料与已派工人员；历史执行记录不能被覆盖。

## 三、两套 Web 和一个现场终端

| 端 | 使用者 | 只保留最重要的入口 |
| --- | --- | --- |
| 配置中台 Web | KANPACE 实施人员、工厂管理员 | 选择行业与工厂类型、导入本厂样本、确认岗位／工序／规则、开通独立工厂实例、查看配置版本 |
| 工厂 Web | 老板、厂长、技术员、排程员、仓库、质检 | 订单与资料、图文拆单、物料与排程、派工与现场异常、交付与总看板 |
| 智能胸牌 | 每位工人一块 | 当前任务大字大图、相关图纸、开工／暂停／恢复／完工、异常反馈、贴标核对和归还 |

中台已纳入此前调研的 19 个行业作为**待本厂确认的参考模板**；模板可以加速首次配置，不等于 19 个行业已有经过验证的自动拆单能力。每个工厂的订单、图纸、人员和数据应独立存储、授权，不能拿其他工厂的数据填充本厂系统。

## 四、按使用顺序排列的需求

状态口径：**已有基础**指代码存在且有相应测试；**部分实现**指仍缺真实业务闭环或存在限制；**待做／待验证**不能向客户宣称可用。以下“验收”是用户可以亲自验证的结果，不是技术名词清单。

| 编号 | 用户要完成的事 | 应有行为与验收点 | 当前判断 |
| --- | --- | --- | --- |
| 01 开厂 | 选“展柜工厂／机械设备工厂／工程现场”等类型；上传岗位人员表、典型订单及排程表 | 系统生成可修改的本厂岗位、工序、关系和首版工作区；数据只进入该工厂 | 部分实现：有独立实例和行业参考配置，真实工厂首开体验需试点 |
| 02 建单与渐进录入 | 按客户实际节点陆续上传效果图、施工图 DWG／PDF、工程图 SLDASM／导出件、BOM、排程等 | 资料按项目和版本归档，能看到完整清晰的效果主图；新文件到达后提示受影响范围 | 部分实现：归档和多格式识别已有；DWG／SLDASM 原件直读未达到可靠拆单 |
| 03 图纸理解 | 效果图看整体样貌，施工图和工程图核尺寸、材料、做法；同一构件能对照多张相关图 | 上传后立刻有预览／识别反馈，不是只显示文件名；重复原图识别为同一依据；原图位置可回查 | 部分实现：PDF 文本和来源坐标较完整；CAD 转图与跨图对照仍需加强 |
| 04 真实三维 | 有设计端真实三维文件时旋转查看、选择部件、关联清单 | 显示来源模型及版本；不能用效果图推论或拼出冒充 CAD 的模型 | 部分实现：STEP 辅助几何核对；原生 `.max`／SLDASM 不能通用直接解析 |
| 05 智能拆单 | 识别构件、数量、尺寸、材料、工艺、所属工种和前后工序 | 形成**图文对应**的构件清单、候选工种任务及来源证据；不确定值明显提示技术员复核，不能直接下料 | 部分实现：表格／PDF 文本及规则产生候选，真实 DWG／SLDASM 自动拆单准确率未证实 |
| 06 工种过滤 | 木工只看木作相关内容，五金、玻璃、灯光各看自己的任务 | 任务卡显示对应构件、尺寸、材料、图纸和效果参照；木工任务不混入不锈钢拉丝板等非本工种描述 | 部分实现：任务文字可按工种过滤，原图局部仍可能含其他工种标注 |
| 07 人工复核与版本 | 技术员确认构件、尺寸、材料、工艺后发布 | 发布前核对来源和工程版本；改版记录保留，能看变更波及的任务；版本页只需版本与记录 | 部分实现：有审核／版本基础，完整影响分析仍要实单验证 |
| 08 物料与库存 | 拆单后算出物料用量，对照库存 | 清楚列出缺口和采购草稿；缺料也可由现场工人反馈 | 已有基础，真实库存准确性和采购流程需客户数据验证 |
| 09 Excel 排程 | 上传实际生产排程表，自动关联项目名、项目图和工序 | 识别并展示流程关系、并行／串行、节点预估时间；可手改或上传新 Excel 覆盖工作版，并预览差异 | 部分实现：导入、差异、模板关系和周期计算已有；不能称任意 Excel 的因果关系可自动准确推断 |
| 10 插单与改派 | 急单直接在排程表调整顺序、时间和人员 | 系统重算冲突、关键路径与受影响订单；不另设难理解的“产能与插单”孤岛页面 | 部分实现：排程与资源计算已有，现场变更闭环需实测 |
| 11 人员导入 | 人员 Excel 只有车间、岗位、姓名也能用 | 自动识别表头，缺员工号自动生成，用户只需上传、预览、确认；人员变动可更新，不强迫逐字段映射 | 已有基础，仍需在真实人事表上检验误匹配与同名人 |
| 12 整项目派工 | 管理者核对工人数与胸牌数，按项目一次下发 | 系统按已确认任务和工种自动挑相关图，不要求人工逐张选效果图／图纸；已发货项目不出现待派列表 | 部分实现：项目派工与设备联动代码已有，实际多胸牌班次未验收 |
| 13 胸牌看图作业 | 工人一眼看出“做哪件、做多少、看哪张图、怎么验收” | 首屏大字与关键图；可看相关施工图和整体效果图、多图切换；尽量少的页面和按钮 | 部分实现：图册与任务卡有代码，图片经 USB，需实板屏幕和工人走查 |
| 14 现场异常 | 做到一半缺料、质量或设备问题可暂停，改做其他任务 | 回传原因、责任人和处理结果；恢复或改派后不丢原任务进度；插队由排程统一处理 | 有基础，异常到复工的真实班次闭环待验证 |
| 15 完工贴标 | 按当天任务完成一件确认一件，给过程件／成品贴唯一二维码 | 标签与订单、构件、版本、工序一一对应；胸牌核短码、质检可追溯 | 部分实现，扫码枪／摄像头自动识别能力不能当作现状 |
| 16 交付回收 | 质检、包装、发货后关闭项目并收回胸牌 | 完成／已发货项目退出发任务列表但历史可查；胸牌当日归还数可核对 | 有业务基础，完整实单验收待做 |
| 17 全局大看板 | 老板看所有订单，不必进每个子页面寻找问题 | 交期风险、卡点、缺料、异常责任人、工序进度及经营 BI 集中呈现；文字少且下一步明显 | 部分实现：有总览和 BI，指标与日常决策匹配需试点 |
| 18 操作 Agent | 用自然语言快速完成查找、汇总、建议和有限的可审操作 | 能解释“依据是什么、缺什么、下一步是谁”；正式改计划或派工保留确认和追溯 | 部分实现：编排基础存在，不能称可自主完成全套拆单或替代技术员 |
| 19 系统互联 | 先与工厂现有 Excel／CSV 往返，未来再接既有 ERP／MES | 导入导出少映射；对具体客户系统调研 API／CLI／MCP 能力，再按授权接入 | Excel 已有基础；通用 ERP／MES 直连待目标系统确定 |
| 20 数据与交付 | 可在另一台电脑查看独立演示版，交付最新代码与必要资料 | 工厂与中台分别有可用 Web；数据隔离、登录权限、第三方许可证与版本说明清楚 | 本地与 Web 模式已有；公网部署、备份恢复、并发容量仍需单独验收 |

## 五、胸牌的具体产品要求与边界

- **外观参考**：用户提供的深色圆角竖屏样机，侧面控制件与摄像头位置要兼顾 IO 空间；它是设计方向，不等于现有 ESP32-C3 开发板已经具备对应结构。
- **信息层级**：第一眼看到工种、当前构件／工序、数量与关键图；无线连接只保留清楚的 Wi-Fi 图标；尽量不用“进度以网页记录为准”一类无帮助提示。重要动作可用简洁弹窗确认。
- **实际操作**：领取并绑定一人一牌、收任务、看图、开工、暂停／换任务、恢复、完工、贴标核对、归还。设备收件 ACK 与工人开工／完工是不同事件。
- **通信现状**：ESP32-C3 开发板的中文任务显示曾由用户确认；早先因 VPN 路由选择保留 VPN、用 USB 做现场测试。现有代码支持 USB／Wi-Fi 任务接收；图片传输和报工主要经 USB。不能把 Wi-Fi 全业务链路说成已实测。
- **摄像头**：拍照、录像、粗略质检是后提出的硬件方向；“流程中拍摄去掉”指不要把拍摄设为每单必经生产节点。摄像头能力尚未在本版开发板上实现或验证。

## 六、已经明确要求删去、移动或收敛的设计

1. **资料导入不放成本报价**；报价若保留，应在确有业务需要时有独立入口。
2. **无真实来源的工程模型不要占主流程**；工程模型入口应接真实 CAD／STEP 来源，不能拿渲染图臆造 3D。
3. **“产能与插单”不另设绕路操作**；插单在生产排程里修改谁先谁后。
4. **“开工检查”若不能说清要检查什么，不应成为形式化关卡**。
5. **版本记录页只显示版本与变更记录**，不要塞成本、任务草稿、其他流程说明。
6. **派工按项目整体下发**，不让管理者再次手动逐张挑图；工种图册由系统按已核对任务生成。
7. **生产流程不强制拍摄**；日后相机可用于主动取证与粗检。
8. **移除多余菜单、长段说明和专业术语**；最常用的上传、核对、排程、派工、异常、交付要直接可达。
9. **不要只交静态 HTML 或 PDF**；产品是可交互 Web，说明文档放企业飞书，代码包与运行入口另行交付。

## 七、截至 2026-10-04 的可证实能力与缺口

本工作区新增十步 Web 工作流、来源化文档识别和状态提示；原有工厂端、中台、Excel 人员导入与自动员工编号、排程表导入／差异预览、模板工序和周期、库存缺口、项目派工与设备桥接可继续使用。OR-Tools CP-SAT 和 LangGraph 有独立运行测试；自动化回归使用合成数据通过。参见 [升级实施记录](../upgrade/软件升级实施记录-20261004.md)、[自动拆图能力边界](../engineering/真实自动拆图算法.md)。

最重要的缺口不是再加菜单，而是用真实订单证明“**从效果图＋施工图＋工程图到图文构件清单，再到干净的工种任务**”是否准确、可复核、节省时间。DWG／SLDASM／`.max` 原件还不能普遍直接生成可靠的生产 BOM；排程关系大量依赖展柜模板；Docling／PP-OCR／PaddleOCR-VL 的真实模型没有在本版部署；本次软件升级没有重新刷写硬件或做多胸牌工厂验收。不存在可公开承诺的拆单准确率、节省工时比例或投资回报率。

此前要求研究并集成可商用开源底座，重点是**用算法提高证据读取、几何核对、排程、排料和受控 Agent 的质量**，而不是把项目名写进页面就算具备能力。历史五项选型是 PaddleOCR、Open CASCADE、Google OR-Tools、PackingSolver、LangGraph：当前工作区已实测 OR-Tools 和 LangGraph 独立运行时；Open CASCADE 与 PackingSolver 保留适配但本次未重装复测；OCR 新服务仍待部署。各组件及模型权重须逐版本核对商用和分发许可。算法学习可使用本厂人工修订与异常结果，但跨工厂训练或复用客户资料必须有单独的数据授权与隔离机制。

## 八、建议的真实验收主线

用此前提供的完整展柜订单做盲测：经过授权的四类历史订单（具体客户名称由所属工厂单独保存）。每单按资料实际到达顺序录入，保留原图和工程师人工拆单作为对照；用一份持续更新的排程表做改单、插单和人员变动演练。已经完工的历史订单应标明**演示复盘**，新增排程项目若是虚构的必须明确标注演示，不能混作真实在产订单。

同一条业务线分别由三种视角检查：首次使用者是否不读文档也能找到下一步；专业测试是否完成建单、BOM、复核、发布、派工、报工和异常恢复且状态持久；展柜业务人员是否认可图纸、物料、排程、质检和发货的交接条件。记录每单的构件漏拆／误拆、尺寸材料改动、跨工种污染、复核用时、任务触达和异常关闭时间，再决定下一版算法投入。

## 九、下一版最应集中解决的五件事

1. **图纸到构件证据链**：解决真实 DWG／SLDASM 输入或明确可靠的设计端导出规范，保留原页／实体定位与版本。
2. **图文构件清单与工种纯净度**：每件有图、有尺寸材料、有依据；每个工种只收自己的任务，跨工种交接可见但不混入作业内容。
3. **渐进资料和排程更新**：客户确认、工程改版、Excel 覆盖、人员变动都能计算影响并安全重排。
4. **整项目派工到胸牌的真实班次闭环**：核人数与牌数、任务及多图到达、暂停换单、贴标和归还逐项实测。
5. **给老板的极简工作台**：只显示今天需要决定的交期、缺料、异常和下一动作；Agent 帮找依据和执行受控操作。
